# 物流管理操作与上线指南

本文面向后台管理员、仓库/工程师和部署人员，说明物流模块的实现、日常操作和正式上线要求。

## 1. 模块如何工作

每张维修工单有两段物流：

- **客户寄入**：客户把设备寄往维修中心，数据保存在 ship_out_info。
- **后台回寄**：维修中心把设备寄回客户，数据保存在 ship_back_info。

后台“物流管理”包括批量导入、异常预警和物流台账。运单写入工单后，系统会尝试实时验单并订阅快递100推送。合法回调更新轨迹缓存；重复或乱序推送不会覆盖较新的轨迹。同一运单如果匹配多个工单或同时匹配寄入、回寄两段，系统拒绝自动更新，避免串单。

### 1.1 快递签收不等于设备入库

快递100报告“已签收”时，系统只把包裹标记为**待入库**，不会直接把工单改成“已签收”。工作人员核对包裹、设备数量和 SN 后，在台账点击“确认入库”，工单才进入已签收状态。

“导入签收单（客户寄入）”表示工作人员已经线下核对完成，因此导入成功后会记录确认人和确认时间，并把工单更新为已签收。

### 1.2 完结与留档

工单进入“已完成”后不会物理删除或迁移：订单、两段物流、轨迹缓存、时间线和操作记录继续保存在数据库中，可通过后台工单、物流台账和导出文件查询。已完成或已取消工单不再作为进行中提醒展示；已完成工单也不会继续产生在途物流异常待办。

## 2. 角色权限

| 操作 | 允许角色 |
| --- | --- |
| 查看配置状态、异常、轨迹和台账 | 超级管理员、管理员、工程师、财务、客服 |
| 批量导入物流、登记回寄发货 | 超级管理员、管理员、工程师 |
| 确认设备入库 | 超级管理员、管理员、工程师 |
| 导出台账 | 所有可查看工单的后台角色 |

前端隐藏无权入口只是体验控制，云函数仍会校验 token 和角色权限。

## 3. 日常操作

### 3.1 客户寄入与自动签收

1. 客户在小程序填写寄件物流，公司、运单号和手机号随工单保存。
2. 系统校验运单并尝试订阅快递100；第三方临时不可用时主流程继续，但后台会显示降级或警告。
3. 快递轨迹更新后，后台“物流台账”显示最新状态和时间。
4. 快递签收后，台账出现“待入库”。仓库核对实物无误后点击“确认入库”。
5. 如果包裹、设备或 SN 不一致，不要确认入库；先记录备注并联系客户。

人工已经确认入库后，晚到的快递签收回调不会把状态退回“待入库”。

### 3.2 Excel 批量登记客户寄入签收

1. 打开“物流管理 → 批量导入”。
2. 选择“导入签收单（客户寄入）”。
3. 下载模板，填写后上传 xlsx 文件。
4. 检查成功、失败和警告明细；失败行修正后单独重传。

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 工单编号 | 是 | 必须与后台工单号一致；同一文件不能重复 |
| 物流公司 | 是 | 使用常见中文公司名，如顺丰、中通、圆通 |
| 物流单号 | 是 | 会做格式、实时验单和重复绑定检查 |
| 签收时间 | 否 | 未填写时使用导入时间 |
| 备注 | 否 | 只写必要业务说明，不填写密钥或完整 token |

单次最多 **50 条**。每行可能执行实时验单和订阅请求，超过上限时拆分文件，避免云函数执行超时或部分成功后请求超时。

批量处理不是数据库事务：成功行会保留，失败行会在结果表中列出。修正后只重传失败行，不要把整份原文件反复导入。

### 3.3 后台回寄发货

1. 确认维修、检测和报价流程已经完成。
2. 收费工单必须先由财务确认 payment_status=paid；免费或明确在保工单可直接回寄。
3. 选择“导入回寄单（后台发货）”，下载模板并填写。
4. 上传后检查结果。系统会拒绝未到账收费单、已取消工单、无效运单和被其他工单占用的运单号。
5. 成功后工单更新为“已回寄”，系统尝试订阅回寄轨迹，小程序端可查询回寄信息。

快递100未配置或临时不可用时，系统可能允许登记并返回“实时验单未完成”警告。上线环境应处理警告并在服务恢复后刷新轨迹，不能把警告当成已验真。

### 3.4 查看轨迹与刷新

在“物流台账”点击寄入或回寄栏的“查看轨迹”。默认优先读取缓存；需要立即查询时点击“刷新轨迹”。物流公司、运单号和手机号只从订单存量数据读取，前端不能传入其他工单的数据。

### 3.5 异常预警处理 SOP

| 预警 | 建议处理 |
| --- | --- |
| 48 小时未揽收 | 核对客户是否真正交寄、单号和公司是否录错；联系客户或快递 |
| 72 小时停滞 | 确认最后轨迹；联系承运商并在工单备注记录处理结果 |
| 服务商异常 | 检查物流页顶部配置状态、快递100账户和云函数日志；不要反复改写运单 |
| 运单冲突 | 搜索该运单关联的工单，修正录错的源数据后再等待或重试回调 |

处理完成后刷新轨迹和异常列表。预警是动态计算结果，不需要手工删除。

### 3.6 查询与导出留档

物流台账支持按状态和关键词筛选。关键词可匹配工单号、客户和运单号。“导出台账”会分页拉取当前筛选范围并生成 CSV；如果提示达到扫描上限，应缩小筛选条件后分批导出。

## 4. 正式环境配置

正式服务空间为支付宝云 uniCloud：env-00jy6g4qwi94。在服务空间全局环境变量中配置：

| 环境变量 | 用途 | 正式上线要求 |
| --- | --- | --- |
| EXPRESS_PROVIDER | 物流适配器 | 固定为 kuaidi100 |
| KUAIDI100_KEY | 实时查询与订阅授权 | 必填 |
| KUAIDI100_CUSTOMER | 快递100 customer 授权码 | 必填 |
| KUAIDI100_CALLBACK_URL | 接收订阅推送的公网地址 | 必填 |
| KUAIDI100_CALLBACK_SALT | 回调签名密钥 | 必填，至少 32 位随机字符串 |

不要把真实值写入 Git、文档、前端 VITE_ 变量或截图。回调地址应指向 cicada-express-callback 的 URL 化地址加 /notify。

配置后重新部署：

- cicada-admin-order
- cicada-client-order
- cicada-express-callback

确认 cicada-express-callback/notify 已开启公网 URL 化、HTTPS 可达。PC Admin 使用 VITE_ADMIN_ORDER_URL，或从 VITE_UNICLOUD_BASE_URL/cicada-admin-order 推导接口地址。

## 5. 运行模式与降级

| 模式 | 能力 | 是否允许正式发布 |
| --- | --- | --- |
| live | 实时验单、主动查询、订阅推送、回调更新 | 是 |
| query_only | 可主动查询，但订阅或回调不完整 | 仅临时排障，不建议发布 |
| fallback | 仅本地格式校验和工单时间估算 | 仅应急降级，不建议发布 |

降级不会阻断客户报修。登记物流时如果只是第三方超时，后台会给出 warning；本地格式错误、公司不支持、运单冲突和业务状态不允许仍会被拦截。

## 6. 上线前检查

### 6.1 自动检查

用正式管理员登录 PC 后台，临时取得 adminToken。只在当前 PowerShell 进程注入，不要提交或长期保存：

    cd pc-admin
    $env:ADMIN_CHECK_TOKEN='<临时管理员 token>'
    $env:LOGISTICS_EXPECT_MODE='live'
    npm run check:logistics
    Remove-Item Env:ADMIN_CHECK_TOKEN

脚本调用受鉴权的 getLogisticsReadiness，只打印能力状态和缺失变量名，不返回或打印快递100凭证。正式发布必须显示三项均为 [ok] 且模式为 live。

同时执行：

    cd docte-master
    npm run check

    cd ..\pc-admin
    npm run build
    npm run check:urls
    npm run check:security

### 6.2 真实业务验收

1. 客户填写寄入运单，后台和小程序立即可查询。
2. 等待或模拟揽收、签收；确认快递签收只进入“待入库”。
3. 后台确认入库；刷新两端，工单进入“已签收”。
4. 收费测试单未到账时导入回寄单应被拦截；核销后再次导入成功。
5. 对同一回调重复推送、先新后旧推送，确认轨迹不重复、不倒退。
6. 尝试把同一运单绑定不同工单，确认第二次录入失败。
7. 完成工单，确认小程序不再显示进行中提示，但历史工单和后台台账仍可查询。
8. 用客服、财务账号确认看不到导入入口，直接调用导入接口也被后端拒绝。

## 7. 排障与回滚

### 配置状态为降级

运行 npm run check:logistics 查看缺失项；在正确的服务空间补齐变量后重新部署三个云函数。不要通过在前端填写密钥修复。

### 查询失败但工单可操作

保留现有运单数据，查看快递100账户状态、手机号校验要求和云函数日志。服务恢复后在轨迹抽屉点击刷新。不要为了刷新重复导入同一工单。

### 回调持续返回 500

搜索日志中的“同一运单号匹配到多个工单或物流段”。先修正冲突工单，再由服务商重推或后台主动刷新。500 是保护性失败，不能改成静默选择第一张工单。

### 需要回滚

保留数据库和轨迹数据，回滚到上一稳定版本的三个物流相关云函数和 PC Admin 静态产物。回滚期间可使用人工登记并保留 warning，但不得关闭付款拦截、回调验签或角色权限。恢复后对回滚窗口内的运单逐一刷新核对。

## 8. 发布证据

每次发布至少保存：Git 提交号、三个云函数部署版本、PC Admin 构建版本、check:logistics 脱敏输出、真实运单验收截图、合法与非法签名回调结果，以及测试工单最终留档查询结果。
