# 牙医仪器检修系统上线测试与验收手册

> 文档版本：1.0  
> 编制日期：2026-07-21  
> 适用版本：`docte-master` 小程序、`pc-admin` 管理后台及共用 uniCloud 后端  
> 正式云空间：`cicada-aftersales`（`env-00jy6g4qwi94`）  
> PC 管理后台：`https://admin.cicadadental.cn`

本文档用于组织正式上线前测试、记录测试证据并作出发布决定。测试人员应逐项填写结果，不得仅凭“页面能打开”判定通过。

## 1. 上线结论速查

只有同时满足以下条件，测试负责人才能填写“允许上线”：

- [ ] 所有 P0 用例通过，没有“失败”或“阻塞”。
- [ ] P1 用例全部执行；未解决的问题已有负责人、解决时间和书面风险接受结论。
- [ ] 小程序和 PC 后台构建成功，所有自动检查通过。
- [ ] `superadmin/admin/engineer/finance/support/client` 权限验证通过。
- [ ] 报修、报价、付款、维修、回寄、完成、评价和开票主链路至少完整走通一次。
- [ ] 微信支付真实小额交易及回调至少成功一次，并完成退款或财务留档。
- [ ] 5 套微信订阅消息完成真机授权、触发、送达和日志核对。
- [ ] 快递100真实单号查询和回调验签至少成功一次；未开通实时轨迹时已有明确降级方案。
- [ ] 生产数据库关键索引及字段类型已在控制台人工复核。
- [ ] 没有真实客户数据误删、越权访问、敏感信息泄露或资金数据不一致。
- [ ] 小程序已上传审核版本，版本号、提交说明和本次验收版本一致。
- [ ] 已明确发布负责人、观察窗口和回滚负责人。

任一 P0 用例失败时，默认结论为“不允许上线”，不得以口头承诺代替修复和复测。

## 2. 测试范围

### 2.1 本次必须覆盖

- 微信小程序：登录、首页内容、地址、报修、SN 识别、设备、工单、报价、付款、物流、收货、评价、发票、投诉建议和账号退出。
- PC 后台：首页待办、工单、客户、库存、财务、结算、发票、物流、知识库、员工、反馈、经营汇总、审计和设置。
- uniCloud：鉴权、角色权限、订单状态机、数据写入、URL 化接口和错误返回。
- 第三方服务：微信登录/支付/订阅消息、快递100；发票由财务在电子税务局人工开具，不对接自动开票服务商。
- 数据库：关键索引、唯一性、客户身份桥、设备 SN 规范化、库存幂等、审计日志和分页总数。
- 非功能项：安全、异常恢复、兼容性、弱网、重复提交和发布后冒烟。

### 2.2 不作为本次上线通过依据

- 仅看本地 Mock 数据得出的结果。
- 仅看 HBuilderX CLI 显示“初始化云数据库完成”得出的索引结论。
- 自动电子开票不在产品范围内；后台只保留对公转账订单的人工发票登记流程。
- 万级并发、灾备演练和长周期压力测试；这些属于后续容量治理，但不能替代本次核心业务验收。

## 3. 测试规则与记录方法

### 3.1 优先级

| 优先级 | 定义 | 示例 |
| --- | --- | --- |
| P0 | 失败会阻止上线 | 无法登录、无法报修、金额错误、越权、支付回调失败、订单丢失 |
| P1 | 核心能力或高频操作 | 筛选导出、库存预警、反馈闭环、订阅消息 |
| P2 | 低频或体验问题 | 空状态文案、非关键布局、辅助提示 |

### 3.2 结果状态

统一使用：`未执行`、`通过`、`失败`、`阻塞`、`不适用`。

`不适用`必须写原因；`阻塞`必须写阻塞方和预计解除时间。失败用例修复后，应保留原失败记录并新增复测结果。

### 3.3 每条用例的证据

至少保存以下一种证据：页面截图、真机录屏、接口响应、数据库记录截图、订阅消息截图、支付商户单号、物流轨迹截图或导出文件。涉及手机号、地址、支付凭证时应脱敏。

建议的证据目录命名：`测试证据/2026-07-21/<用例ID>/`。

- 测试订单、客户和反馈必须带明显 QA 标记。
- 不得删除或修改真实客户、真实订单和真实库存。
- 支付测试使用业务允许的最低有效金额，测试前由财务确认，测试后核对退款或记账结果。
- 取消账号、注销客户、批量导入、退款等不可逆或高风险操作只能针对专用测试数据。
- 云函数日志、浏览器控制台和截图不得包含完整密钥、Token、身份证明或支付私钥。

## 9. 端到端主链路

以下用例必须使用同一张工单连续执行，不能拆成互不关联的页面截图。

### E2E-01 标准微信支付维修流程（P0）

1. CLIENT-A 登录并同意必要隐私条款。
2. 使用在保或过保设备提交报修，上传至少一张故障图片。
3. 确认小程序、后台、`cicada_orders` 中订单号一致，客户和设备自动关联。
4. 客户填写寄出物流；后台确认入库并指派 ENG-A。
5. ENG-A 进入检测，填写设备信息，添加配件/服务/其他费用并发布报价。
6. CLIENT-A 查看报价明细并接受，确认最终支付金额一致。
7. CLIENT-A 发起微信真实小额支付；确认支付成功页、微信商户记录和服务端订单状态一致。
8. 后台确认付款状态、库存扣减和库存流水均正确。
9. ENG-A 推进维修状态并填写时间线；后台登记回寄物流。
10. CLIENT-A 查看真实物流轨迹，收货后确认收货并评价。
11. 后台完成工单，核对订阅消息和完整审计轨迹。

预期：全流程没有人工改库；金额、状态、库存、物流和时间线一致；重复刷新不会重复支付、扣库或发送错误状态。

### E2E-02 转账凭证及驳回重传（P0）

1. 创建并发布另一张报价工单。
2. CLIENT-A 上传付款凭证。
3. FIN-A 查看凭证并填写原因驳回。
4. CLIENT-A 看到驳回原因并重新上传。
5. FIN-A 核销付款。

预期：每次凭证、状态、驳回原因和操作者可追溯；仅最终核销时扣减一次库存。

### E2E-03 发票闭环（P0）

1. CLIENT-A 对符合条件的测试订单提交发票申请。
2. FIN-A 在发票管理查看申请并核对抬头、税号、邮箱和金额。
3. 使用人工登记流程将状态改为已开具，并填写发票信息。
4. CLIENT-A 刷新后查看状态和电子发票地址。
5. 核对四流台账中的发票与订单、付款金额一致。

预期：只触发 `order_completed` 对应的完成/发票提示，不应出现已下线的 `invoice_issued` 独立订阅场景。

### E2E-04 投诉建议闭环（P1）

1. CLIENT-A 提交关联测试工单的投诉。
2. SUP-A 分配处理人、设置紧急度、回复并记录回访。
3. 未回访前尝试结案，确认被拒绝；回访后完成结案。
4. CLIENT-A 查看回复和最终状态。

预期：前后台状态映射正确，每个动作写入 `cicada_order_events`，处理记录可审计。

### E2E-05 跨用户隔离（P0）

1. CLIENT-A 创建工单、设备、地址、发票和投诉。
2. CLIENT-B 正常登录，通过页面和直接接口分别尝试访问这些记录。

预期：CLIENT-B 看不到 CLIENT-A 的任何数据；服务端按用户身份校验资源归属。

### 13.3 发布后 24 小时观察

- 登录、报修、支付、物流回调和订阅消息失败率是否异常。
- 是否出现重复订单号、重复扣库存、重复支付或状态倒退。
- URL 化接口是否出现集中 401、404、5xx 或跨域错误。
- 快递回调是否被错误验签大量拒绝。
